## Reviewer output (verbatim)

What this design does: It replaces the confirmation module’s caller-supplied BLS and line-266 functions with one record produced by a separate, pinned verifier. The approach preserves the calibration image, but **rev 1 does not yet close R14S4-S-1**: it moves the decisive checks to a process whose output and authority are not fully bound.

**Verdict: FIX.** Independent design feedback only; no approval.

### Findings

**SV1-S-1 — BLOCKER — The expected record hash has no authoritative source.** In [§§2, 4 and Q2](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:24>), a caller controlling the proposed “governing input manifest” could replace both a forged record and its expected SHA-256; every hash comparison would pass. R-14a item 7 requires governing records rather than caller values, and `seed_disclosure` commits the declaration before the beacon. Putting the record hash into the signed C2 protocol bytes is also circular: the record contains `protocol_hash`, which would then depend on the record’s hash. **Correction:** specify a signed-C2-authorized, authenticated, append-only *post-beacon* acceptance record for the verification hash, and require the slice-6 loader to resolve that record before any gate. A repository commit alone does not identify which commit governs.

**SV1-S-2 — BLOCKER — The record can assert that verification happened.** [§§3–5](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:38>) let an attacker controlling a verifier run write `bls_verified: true`, an arbitrary 64-hex `seed_l266`, and the expected code and image identifiers into a canonical record. Re-running the same compromised image can reproduce those bytes. The module’s pins check claims *in the record*, not the bytes that ran. This leaves the R-8 frozen-function and R-14a item 7 checks unauthenticated. **Correction:** bind reviewed verifier source, exact executed bytes, engine inventory, dependency lock and actual image identity at verifier launch; independently rebuild or validate that identity for the rerun and retain its input/output attestation. Check `engine_commit` and `image_digest` at the consumer too. State in the signed contract whether authenticated external verification satisfies item 7’s “verifies itself” wording. The route can transfer trust to a verified process; it cannot eliminate that trust.

**SV1-S-3 — BLOCKER — The separate runtime needs a governance binding.** [§3](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:40>) calls the real `preregistration.trial_seed`, which respects R-14a item 4’s call requirement. But R-8 binds that function at the D-19 engine commit **on the qualification object’s pinned runtime and image**. Calling it in a new image is not literal compliance merely because the source file is identical. The same-image rule independently keeps C2’s real evaluation on the existing calibration image; the design correctly leaves that image untouched. **Correction:** obtain an explicit owner-governed interpretation or exception for this external computation in the signed C2 contract, while retaining the engine-commit byte check and existing evaluation image. This is a governance proposal, not a code fix the reviewer can approve.

**SV1-S-4 — BLOCKER — Matching two supplied inputs does not authenticate either.** [§§3–4](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:53>) compare chain metadata, capture time and trials in the record with the module’s “own inputs.” If those inputs and the verifier run both receive a substituted capture, both can select the same wrong round and pass. The record also omits the chain hash and scheme, although `seed_disclosure` fixes the chain by hash and public key at signing. **Correction:** name and test each authoritative loader source: signed chain hash/key and matching metadata, freeze-point acceptance record for the earliest qualifying CDX capture, and posted declaration for ordered trial identities. Compare the record to those authenticated values, including chain hash and scheme; reject missing or extra identity fields.

**SV1-S-5 — BLOCKER — The BLS message is unspecified.** [§3](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:46>) correctly names quicknet’s G1 signature, G2 key and RFC 9380 domain tag, but does not say what bytes the library verifies. Drand’s verifier hashes the **eight-byte unsigned, big-endian round number with SHA-256**, then verifies the G1 signature over that digest with the stated tag. Feeding the raw round or selecting a library’s G2-signature default rejects genuine output. This is essential to `seed_disclosure.verification`. **Correction:** specify those exact bytes and group/subgroup validation in the verifier contract; pin a known answer to the fixed signed chain as well as negative cases. [Drand’s verifier implementation](https://github.com/drand/drand-client/blob/master/lib/beacon-verification.ts) supports the byte and scheme details.

**SV1-S-6 — BLOCKER — The lockbox handoff is still caller-controllable.** [§§2 and 7](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:24>) show a sealing record but do not specify how its `seed_l266` and family seed are bound to the verified confirmation result. The present [`_check_identity`](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/calibration/c2_lockbox.py:634>) compares the nominee with `Request.seed_l266` and derives the stream from `Request.family_seed`; matching fabricated request and artifact values can satisfy those local checks. [OWNER_DECISION_R14L5_S2](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/OWNER_DECISION_R14L5_S2.md:1>) instead requires the seed from the sealing record after confirmation verification. **Correction:** require sealing to carry the accepted verification-record hash and resulting seeds; require the slice-6/store handoff to resolve the immutable sealing entry and populate the lockbox request from it. Test a coherent substitution of request and artifact values.

**SV1-S-7 — NON-BLOCKING — The proposed verifier environment omits a required import.** [§3](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:40>) says NumPy is unnecessary while importing `c2_confirmation.beacon_round` and `check_beacon`. [`c2_confirmation.py`](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/calibration/c2_confirmation.py:24>) imports NumPy and `calibration.seeds`, which also imports NumPy; a verifier image without it fails before writing a record. **Correction:** pin NumPy in the *verifier* environment, or avoid that import without copying a governed rule. Also specify how the confirmation module performs `check_beacon`’s local checks after removing its verifier callback; the current function combines local and BLS checks.

**SV1-S-8 — QUESTION — Seven-day evidence is not defined.** Under [§8 Q5](</D:/PMP-programs-for-sharawi/autonomous-quant-trader/review/r14a-modules/DESIGN_SEED_VERIFIER.md:119>), a valid signature first presented after day seven would pass the record checks even if no verifying output existed by the deadline. `seed_disclosure.failure` invalidates that cycle. **Recommendation:** keep this as an operational gate, but name the dated, independently checkable evidence of availability within seven days and require its check before evaluation. A signature alone proves validity, not when it became available.

### Open questions and simpler route

| Question | Recommendation |
|---|---|
| Q1 library | Prefer a maintained binding that exposes the **G1-signature/G2-key** variant, explicit DST, point validation and reproducible pinned build. `blst` is a candidate; its Python packaging and exact call must be demonstrated before selection. `py_ecc` needs the same interoperability and provenance review. Do not choose by a generic “BLS verify” API or one positive vector alone. |
| Q2 hash binding | Use the authenticated post-beacon acceptance route in SV1-S-1. Do not add this hash to protocol bytes whose `protocol_hash` the record contains. |
| Q3 §16 | Treat the verifier as protected protocol-enforcement logic and obtain different-model and human PR review before merge. |
| Q4 rerun | Use a second host or CI identity that validates or independently rebuilds reviewed bytes and pins, records actual runtime identity, and compares canonical bytes. The same image twice is insufficient evidence on its own. |
| Q5 deadline | Keep the seven-day invalidation rule and bind the dated availability evidence described in SV1-S-8. |

One verifier and one canonical record remain a reasonably small route under the fixed calibration image. The essential additions are an authoritative hash handoff and proof of what verifier code actually ran; adding more seed formulas or a second verification record would not solve those gaps.
