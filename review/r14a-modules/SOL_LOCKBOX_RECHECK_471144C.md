### Findings

1. **R14L2-S-1 — BLOCKER: trial index remains caller-controlled.** [c2_lockbox.py:631](D:/PMP-programs-for-sharawi/autonomous-quant-trader/calibration/c2_lockbox.py:631) compares the artifact index with `Request.trial_index`; neither `_check_trial` nor `run_evaluation` verifies that request value against the immutable C2 trial record. In a synthetic check, changing both indices from 3 to 4 and recomputing the seeds and artifact hash returned `PASS` against the unchanged trial object. Annex D §D-3.2 and §D-3.5 require the seed to derive from the nominee’s recorded index. **Impact:** a coherently wrong fit seed passes pre-read. **Minimal correction:** retrieve and verify the immutable C2 trial record, then take its index into the seed derivation. The new test changes only the artifact, so it misses this case.

2. **R14L2-S-2 — BLOCKER: acceptance is asserted, not verified.** [c2_lockbox.py:978](D:/PMP-programs-for-sharawi/autonomous-quant-trader/calibration/c2_lockbox.py:978) binds the record to the supplied transaction and checks `first_post: true` and `confirmations >= 6`. That is a useful partial repair of R14L-S-3. A caller can still fabricate those assertions; I also confirmed that `block_hash: null` and `height: "not-a-height"` pass. The test fixture itself uses an all-zero block hash. R-14a item 2 requires verification of the *accepted* post; O-6a SPEC §§3–5 defines node-backed post order, inclusion, and acceptance evidence. **Impact:** `start()` can treat an unverified post as accepted. **Minimal correction:** have the owner specify an authoritative acceptance-evidence handoff under §16, verify its provenance and binding before `start()` accepts it, and validate the schema fields. The author is right that the worker need not run a Bitcoin node; the current record alone does not close the requirement.

3. **R14L2-S-3 — NON-BLOCKING: startup can append a record with a mismatched image digest.** [c2_lockbox.py:1232](D:/PMP-programs-for-sharawi/autonomous-quant-trader/calibration/c2_lockbox.py:1232) passes the caller’s `image_digest` to `record_startup` without comparing it with the signed digest. On a qualified image with passing vectors, a different supplied digest would produce a `PASS` startup record for that digest. Annex D §D-3.4 binds startup to the module hash and image; DESIGN §6.3 checks image identity before a read. The later pre-read comparison should prevent a read with that mismatch, but the startup record is misleading. **Minimal correction:** compare the supplied digest with `signed.image_digest` before the append; the launch route must establish how the actual image digest is measured.
