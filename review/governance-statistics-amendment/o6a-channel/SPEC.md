# O-6a: the public channel for the C2 declaration-hash post (specification, revision 1)

**Date:** 2026-10-04
**Drafted by:** Claude Opus 5.5 (`claude-opus-5-5`). The owner delegated drafting choices to the agent on 2026-10-03 and again on 2026-10-04. Every choice below is therefore an `[AI default]`. The channel itself stays `<<OWNER O-6a>>` until the owner answers §8.
**Scope:** the requirements set by `../reg-o8-proposal/PROPOSAL.md` §4 (SR3-2, FR4-2) and DRAFT_WORDING §2.0. It changes no decided row and no frozen file.

## 1. What the channel must do (DRAFT_WORDING §2.0)

The channel must be one identity, named in the protocol and dedicated to C2. That identity must:
1. authenticate its poster;
2. be append-only, with no edit or deletion;
3. carry a third-party timestamp;
4. be captured by an independent archive at posting time.

The declaration cannot choose the channel. The first post governs. A second post, or a mismatched first post, invalidates the cycle.

## 2. Choice: one dedicated Bitcoin key [AI default]

- **Rekor:** rejected, as recorded in PROPOSAL §4.
- **Bitcoin:** the post is a confirmed mainnet transaction, so it meets each requirement:
  - only the key holder can sign it (1);
  - confirmed blocks cannot be edited (2);
  - blocks carry timestamps set by miners, not by the poster (3);
  - every archival node keeps a copy (4).
- **Trusted third party:** this remains the fallback (§8 option B). Without one listable identity, it cannot rule out a private second commitment.

## 3. Definitions

- **Key `K`.** One secp256k1 key, generated by the owner for C2 only, offline, and never used for anything else. Its P2WPKH address `A` is fixed in the protocol at signing: `<<SIGNING: address A>>`.
  - The private key never enters the repository, a log, a prompt or an artifact.
  - Only the address is public.
- **Post.** A post is any mainnet transaction that spends an output locked to `A`.
  - This answers SR3-2: Bitcoin has spends, not posts "from an address", so a post is defined by its spend.
  - An inbound payment to `A` is not a post and authenticates nothing.
- **Well-formed post.** A well-formed post has exactly one OP_RETURN output, whose data push is exactly 37 bytes: ASCII `AQTC2` (5 bytes) followed by the raw 32-byte `declaration_sha256`.
  - This replaces the text message in DRAFT_WORDING §2.0, which was 89 bytes and exceeded the pre-v30 relay default (§6).
  - Its other outputs carry no data. Change goes to an address other than `A`.
- **Order of posts.** Posts are ordered by block height, then by position within the block. Only posts confirmed in the main chain count.
- **First-post rule.** The first post governs. The cycle is invalidated if:
  - the first post is not well-formed;
  - its hash does not match the declaration presented;
  - any later post appears during C2.

## 4. Listing all posts

- **How to list.** Every transaction spending from `A` is found by scanning the main chain for inputs whose previous output is locked to `A`.
  - This can be done with any full node, or with an address index such as Bitcoin Core with `-txindex` plus a scan, or Electrum-protocol servers.
  - Two independent public explorers are also consulted, and their results must agree.
- **Verification.** The verifier records:
  - the raw transaction;
  - the block hash and height;
  - the Merkle path.

  It checks them against block headers it validates itself (Constitution §27 record).

## 5. Time, depth and the beacon round

- **Confirmation depth: 6 blocks.**
  - A post counts once 6 blocks are built on its block.
  - A deeper reorganization that removes or reorders posts is handled by re-applying §3 to the new main chain.
  - If the declaration post itself is reorganized away, the cycle is invalidated, as a failure under §2.0 `failure`.
- **Canonical timestamp `T`.** `T` is the header timestamp of the block that includes the post.
  - A block timestamp must exceed the median of the previous 11 blocks, and nodes reject it if it is more than 2 hours ahead of their clock. `T` is therefore bounded, not exact.
  - The declarer does not set `T`.
  - The 24-hour gap to the beacon round (DRAFT §2.0 `round`) is much larger than that bound.
- **Round.** The beacon round is the first round of the fixed drand chain whose scheduled time is at least `T + 24h`. This is unchanged from §2.0.

## 6. Relay policy (checked 2026-10-04)

**Bitcoin Core 30.0** was released on 2025-10-10. Its release notes, at <https://bitcoincore.org/en/releases/30.0/>, say:
- "`-datacarriersize` is increased to 100,000 by default, which effectively uncaps the limit";
- "It can be overridden with `-datacarriersize=83` to revert to the limit enforced in previous versions";
- "Multiple data carrier (OP_RETURN) outputs in a transaction are now permitted for relay and mining";
- the limit "applies to the aggregate size of the scriptPubKeys across all such outputs in a transaction".

**This post's script is 39 bytes:** 1 byte `OP_RETURN`, 1 byte push length, and 37 bytes of data. It fits under the old 83-byte default and the new one, so it relays under either policy. The earlier unverified recollection (PROPOSAL §4, SR4-1) is now settled by this primary source.

## 7. Funding, cost, custody and privacy

- **Funding.** The owner sends one small payment to `A`, enough for one transaction fee, from a source of his choice.
  - The post spends that payment: the OP_RETURN output carries no value, and the change goes elsewhere.
  - `A` is never spent from again.
  - Payments others send to `A` are ignored and never spent, because spending one would be a second post.
- **Cost.** One Bitcoin network fee, plus any fee charged by the source of the funds.
  - This is the owner's real money. It is separate from L-01, which is the trading capital and stays 0.
  - Fees vary with network demand. No figure is promised here.
- **Custody.**
  - If `K` is lost before the post, C2 cannot be declared. A new channel then needs a new amendment.
  - If `K` is stolen before the post, the thief can post first, which invalidates C2.
  - So `K` is backed up offline and never shared.
- **Privacy.**
  - The post reveals only a hash.
  - Funding from an exchange account can link `A` to the owner's identity at that exchange, and anyone who later sees the declaration can link the post to the project.
  - Funding from a source not tied to him reduces this. That is his choice.
- **No automation.** The app, the repository and the AI never hold `K` or sign with it. The owner makes the post with a wallet of his choice. The repository only verifies it, from public data.
